1Executive Summary

Why police labs, CFSLs and investigating officers need one tool for every CCTV DVR on the market.

NYAYA Forensics is a desktop application that gives law-enforcement investigators a single tool to acquire, parse, recover, analyse and report CCTV evidence from eight major DVR/NVR brands — regardless of their proprietary file systems (DHFS, HIKFS, WFS, UFS) or proprietary video containers (.dav, .hik). Today an examiner juggles four to eight vendor tools, loses deleted footage, and walks into court with a broken chain of custody. NYAYA collapses that chaos into one offline, court-conscious workflow with AI-assisted speed.

The app is built on Tauri v2 (Rust backend + React/TypeScript frontend with Tailwind, vis-timeline and shadcn/ui) with a Python 3.11 forensic core invoked as a sidecar through Tauri commands. It deliberately reuses battle-tested open-source parsers — the drcrecoverydata/dvr_dahua DHFS parser, community Hikvision parsers, the X-Ways DHFS 4.1 X-Tension logic, PhotoRec/Scalpel carving signatures and FFmpeg — instead of re-inventing file-system decoding. Our innovation is the plugin parser architecture, the blockchain-style hash-chained custody log, AI-assisted event correlation and a one-click court-ready PDF.

2Problem Statement & Challenges

The ground reality of CCTV forensics in India — in plain language.

  1. Every vendor speaks a different language. Dahua, Hikvision, Uniview and others each use a proprietary file system (DHFS, HIKFS, WFS, UFS). A tool built for one brand cannot even mount another brand's hard disk.
  2. Videos are locked in proprietary formats. Footage is wrapped in .dav / .hik containers that ordinary media players cannot open; the real H.264 stream is buried under a vendor header.
  3. Deleted footage is nearly impossible to recover. When a DVR overwrites or an accused formats/erases a disk, the recordings are gone unless the examiner carves raw video frames from unallocated space.
  4. DVR clocks are unreliable. The internal clock drifts or is deliberately reset; wrong BCD timestamps make footage inadmissible if the examiner cannot prove and correct the offset.
  5. Chain of custody breaks easily. Manual copying, unverified hashes and loose paperwork violate Indian Evidence Act §65B and let defence counsel challenge the evidence.
  6. Investigators need many expensive tools. DVR Examiner, SmartPSS, Autopsy and OEM utilities each cover only one slice; acquiring and learning them is slow and costly for police stations.
  7. No AI assistance. Reviewing days of footage frame-by-frame for a face or a vehicle wastes manpower; no existing DVR forensic tool highlights the critical seconds automatically.
The court test : an investigating officer's report lives or dies on three things — authenticity (verifiable hash), integrity of custody (unbroken, documented handover) and reliable timestamps (normalised, timezone-correct). NYAYA is engineered around all three from the first line of code.

6System Architecture — 7 Layers

A clean, testable pipeline: every layer consumes JSON and emits JSON, so the Rust commands stay thin and the Python core stays swappable.

Seven layers, end to end

L1 Device ID

Reads the first 20 MB and matches magic bytes against a signature table — DHFS, HIKVISION, WFS, UNIVIEW, plus OEM aliases (CPPLUS, GODREJ, MATRIX, TP-LINK). Returns a vendor record that drives plugin selection.

L2 Forensic Acquisition

Streams a bit-exact copy with dd conv=noerror,sync, hashes MD5/SHA-256 in 4 MB chunks on the fly, and can write E01 via pyewf. Never modifies source media.

L3 FS & Format Parser

Plugin engine with a BaseParser abstract class. Each plugin wraps an existing open-source parser (Dahua → dvr_dahua; Hikvision → community parser; others → generic/FFmpeg). Headers stripped: 32 B Dahua, 48 B Hik.

L4 Recovery Engine

Scans unallocated space for H.264 IDR NALs (00 00 00 01 65), groups hits by ≤2 MB gaps (byte-domain proxy for “PTS gap < 2 s”), slices clips and remuxes with FFmpeg.

L5 Timeline & Correlation

Converts BCD device timestamps to epoch, normalises to IST/UTC, and joins events from multiple cameras with a ±10 s temporal window.

L6 Integrity & Custody

Every action appends an entry to custody.jsonl whose hash chains the previous one — blockchain-style. Any tampering breaks the chain.

L7 AI & Reporting

YOLOv8n (2 FPS) labels objects, InsightFace matches faces, MOG2 flags motion; results merge into events.json and a one-click ReportLab PDF with §65B certificate.

Architecture principle : the Rust layer stays thin (commands, case registry, hashing, custody ledger) while the Python sidecar owns the heavy lifting (parsers, recovery, AI, PDF). Swapping a parser means dropping in a plugin — no rebuild of the Tauri shell.

8Forensic Acquisition Implementation

Write-protected, verified, repeatable — the three non-negotiables.

  • Write-blocking: the original DVR hard disk is connected through a hardware write-blocker; the acquired image is what we process — never the source again.
  • Bit-exact copy: streaming dd with conv=noerror,sync survives bad sectors (whole dd block replaced with zeros, so position is preserved).
  • Streaming hashing: MD5 and SHA-256 are computed while copying in 4 MB chunks — no re-read of the source, verification is built in.
  • E01 support: optional Expert Witness Format output via pyewf so the image opens directly in FTK Imager / Autopsy / Magnet.
  • Hash report: a FTK-style .hashes.txt is written for the case folder, so verification is human-readable in court.
# core/acquisition.py — copy + dual-hash in one pass (4 MiB chunks)
def python_copy_and_hash(src, dst):
    md5, sha = hashlib.md5(), hashlib.sha256()
    with open(src, "rb") as fin, open(dst, "wb") as fout:
        while True:
            buf = fin.read(4 * 1024 * 1024)
            if not buf: break
            md5.update(buf); sha.update(buf); fout.write(buf)
    return md5.hexdigest(), sha.hexdigest()
Why it matters : a single MD5 or single SHA hash is fine, but courts increasingly expect two algorithms and a documented method. The 4 MB chunk size matches the prompt spec and keeps progress reporting responsive.
Note on E01 : pyewf wraps segments with embedded case metadata. NYAYA emits a companion .case descriptor and computes the per-segment CRC then the overall set hash — the same structure FTK Imager produces.

9FS & Format Parsing Strategy

A plugin per engine — wrapping proven parsers instead of rewriting them.

NYAYA defines an abstract BaseParser and registers one plugin per forensic engine. Because CP Plus inherits Dahua and Godrej/Matrix inherit Hikvision, eight brands resolve to two real parsers plus brand mapping. Each plugin calls an existing open-source tool via subprocess (Tauri → Python → parser) and returns a JSON manifest.

class BaseParser(ABC):
    vendor: str                     # "dahua", "hikvision", ...
    magic: bytes                    # b"DHFS", b"HIKVISION", ...
    header_bytes: int               # 32 (Dahua) / 48 (Hik)
    def parse(image) -> Manifest: ...   # JSON manifest of tracks/frames
    def extract(video, out) -> Path:   # strip header -> remux mp4

Dahua (.dav): strip 32-byte header

Dahua frames begin with DH + a 32-byte frame header; the H.264 Annex-B stream follows. The wrapper strips those 32 bytes and lets FFmpeg remux the elementary stream.

Hikvision (.hik): strip 48-byte header

Hikvision wraps H.264 as MPEG-4 with an additional hik tag structure; the first 48 bytes are the container signature & bookkeeping. After removing them, FFmpeg probes and remuxes.

Reuse statement : we deliberately do not implement DHFS or HIKFS from scratch. dvr_dahua (drcrecoverydata), the X-Ways DHFS 4.1 X-Tension algorithm description and community Hikvision parsers already exist and are battle-tested — NYAYA drives them through Tauri → Rust → Python subprocess.
Fallback : when the FS layer is missing (deleted/invalidated), the same plugin reuses PhotoRec/Scalpel signatures to carve surviving file types, keeping evidence out of vendor lock-in.

10Deleted Recovery Engine

Carve footage the file system says is gone.

  1. Scan: walk the raw image for the H.264 IDR start code 00 00 00 01 65 (I-frames).
  2. Group: clustering hits whose byte gap is ≤ join-gap (default 2 MB, the byte-domain proxy for “PTS gap < 2 s” at common DVR bitrates).
  3. Extract: slice each group with seek/read (portable dd skip/seek) into a clip file.
  4. Remux: FFmpeg -c copy wraps each clip into MP4 without re-encoding.
  5. Report: offsets, cluster sizes, IDR counts and confidence land in recovery.json.
IDR = b"\x00\x00\x00\x01\x65"        # H.264 I-frame NAL
offsets = scan(IDR, image)               # chunked, boundary-safe
groups = group_where_gap_lt(offsets, 2*MB)  # PTS-gap<2s proxy
for g in groups: clip = extract(g); remux(clip)
Evidence-grade : recovered clips retain their carve offsets so an examiner can testify exactly where in the disk the footage was found.
Limitation stated honestly : if the DVR encrypted its stream (AES) prior to NAL encapsulation, carving yields ciphertext. NYAYA checks for H.264 Annex-B patterns and flags encrypted/obfuscated regions in the report rather than guessing.

11Timeline & Correlation

Turn flaky DVR clocks into a defensible, court-grade timeline.

  1. BCD → epoch : Dahua/Hik live timestamps are packed BCD (YY MM DD hh mm ss). Each is decoded and converted to Unix epoch.
  2. IST/UTC normalisation : device timezone is recorded with the case; everything is normalised to both IST and UTC so multi-jurisdiction reports agree.
  3. ±10 s multi-cam join : events from different cameras within a ±10-second window are grouped into a "suspicious event" cluster, with the DVR reference clock offset documented so defence can audit the adjustment.
  4. Render : the merged timeline.json feeds vis-timeline in the React frontend — a horizontal, zoomable, filterable view over every camera.
def bcd_to_epoch(bcd_bytes):  # 0x13 0x09 0x04 0x10 0x30 0x22 → 2023-09-04 10:30:22
    y = (bcd[0] >> 4)*10 + (bcd[0] & 0x0F)   # ... per BCD nibble
    ...  # then fold in timezone, apply device offset, emit ISO-8601 UTC
Why ±10 s : DVR clocks drift a few seconds per week; a 10 s correlation window catches the same person appearing on two cameras without fabricating simultaneity.

12Chain of Custody

Blockchain-style hash chaining, §65B-ready.

Every forensic action (acquire → analyse → recover → export → report) appends a line to custody.jsonl. Each entry carries seq, ts_utc, examiner, action, payload_hash and the hash of the entire previous entry:

entry_n.hash = SHA256( prev_hash || payload_n )
# Example entries:
# {"seq":1,"ts_utc":"2025-09-04T10:00:00Z","examiner":"SI R. Kumar",  \
#  "action":"ACQUIRE","payload_hash":"a1b2…","prev_hash":"0"*64}
# {"seq":2,"ts_utc":"2025-09-04T10:12:00Z","examiner":"SI R. Kumar",  \
#  "action":"EXTRACT_DAV","payload_hash":"c3d4…","prev_hash":"a1b2…"}
  • Tampering with any record breaks the chain and is instantly detectable by re-verification.
  • The ledger is written to the case folder and mirrored to the PDF report (section 8) — paper + electronic, per §65B practice.
  • Every hash is a SHA-256 of the canonical JSON payload; the chain never stores the evidence itself.
§65B alignment : the certificate page lists the six statutory declarations (computer operated properly, information fed in ordinary course, verification hashes) — exactly the certificate a court needs before it admits the electronic record.

13AI Analytics

Let the model skim 10,000 hours so the examiner only watches 10 minutes.

YOLOv8n — object detection

Runs at a capped 2 FPS (imgsz 640, conf 0.5) so a day of video analyses in a few minutes. Emits {timestamp, label, bbox, confidence}.

InsightFace · face capture

Detects and embeds faces for person matching across cameras; reference-face search returns ranked candidate frames.

MOG2 · motion detection

Background subtraction flags activity segments, letting the examiner jump to the meaningful seconds instead of scrubbing.

events.json

All three streams merge into one event file that drives the timeline, filters and the PDF — AI never alters the underlying evidence.

17SOPs — 6 Standard Operating Procedures

Field-tested steps anyone can follow; each produces a custody entry.

SOP-1 · Scene Handling

Photo-document DVR, note make/model/serial & CPU state; do not power off a live DVR (may delete cache); label cable ports; seize drive with write-blocker; log scene officer name.

SOP-2 · Acquisition

Hardware write-blocker → Acquire (dd + MD5/SHA-256) → verify hash matches FTK-style output → log to custody chain. No GUI-driven copy of the source.

SOP-3 · Analysis

Load case → vendor auto-detect → select parser plugin → walk FS → review manifest → keep original read-only; export working copies only.

SOP-4 · Recovery

Set scan region (whole disk), join-gap 2 MB, min-clip 256 KB; run carve_deleted; human-verify each clip is valid video; log offsets.

SOP-5 · Reporting

Generate PDF → examine §65B certificate completeness → attach custody log + hashes → twin-out hard/soft to IO & CFSL for confirmation.

SOP-6 · Court

Carry source + working copy + hash report + custody JSONL printout; reproduce verify in court demo; keep chain-of-custody timeline documented.

18User Manual — 9-Step Quick Start

From a hard drive to a court-ready PDF in nine steps.

  1. Create a Case — on page /case fill case name, IO number, examiner, timezone.
  2. Drag-Drop the image — drop the .dd/.img/.E01 onto the acquisition zone.
  3. Auto-Detect — NYAYA scans magic bytes and shows the vendor (Dahua, Hikvision, Uniview…). Confirm the match.
  4. Extract / Parse — the matched plugin parses DHFS/HIKFS/WFS/UFS into playable clips (or run generic NAL scan).
  5. Timeline — vis-timeline shows every clip/event per camera; zoom & filter by day, camera, or AI label.
  6. AI Filter — toggles for Person / Vehicle / Face / Motion; shows matched frames instantly.
  7. Recovery — run Carve Deleted and inspect recovered clips with carve offsets.
  8. Review & Accept — mark each clip kept/flagged; the custody ledger records every action.
  9. Generate PDF — one click produces the 9-section report + §65B certificate; export for evidence package.
Time-to-value : steps 1–4 take about a minute on a modern laptop (image size dependent); AI triage at 2 FPS usually finishes a day of footage in minutes.

Conclusion

NYAYA Forensics turns a shelf full of vendor tools into a single offline, lightweight, court-conscious desktop application. By wrapping proven open-source parsers behind a plugin architecture and the Python sidecar, it stays honest about its boundaries — while its hash-chained custody, BCD-normalised timelines, and YOLOv8n/InsightFace triage attack the exact failure modes that lose cases in court. It is a five-day build aimed at production-lab-grade evidence handling: lawful, auditable, fast.

Final word : the hardest part of CCTV forensics is not the code — it is trust. NYAYA earns trust by never touching source media, by chaining every action to the previous one, and by proving each recovered frame with a hash a court can verify. A one-click PDF then lets the investigating officer walk into the courtroom carrying exactly what a judge needs.
